# Repository layout and build

Settled in [issue #15](https://github.com/MaxAnderson95/macos-enterprise-sso-bridge/issues/15).

## Layout

```
bridge/                 Package.swift, Sources/BridgeCore, Sources/EnterpriseSSOBridge, Tests/BridgeCoreTests
extension/              package.json, tsconfig.json, src/, pages/, manifest.chromium.json, manifest.gecko.json, build.mjs, tests/
identity-providers/     entra.json
packaging/              Info.plist, build-app.sh, build-pkg.sh, install-chromium-extension.sh
tools/                  generate.mjs
assets/                 icon masters, rendered PNGs, the .icns, and make.py
docs/
.github/workflows/
```

Packaging is top-level rather than under `bridge/` because the `.pkg` installs both native-messaging manifests, which name the Chromium extension ID and the Gecko add-on ID. It spans both halves and belongs to neither.

`.gitignore` covers `.build/`, `dist/`, `node_modules/`, and built packages.

## The Bridge's targets

A `BridgeCore` library target and a thin `enterprise-sso-bridge` executable target.

`BridgeCore` holds everything value-shaped: `CallerAuthentication`, the length-prefix framing reader and writer, the request and response codecs, the `IdentityProviderAdapter` protocol with the Entra adapter, and the Handoff state machine. The executable holds `main`, `NSApplication`, the window, and the `WKWebView`, and is deliberately too thin to be worth testing. Tests import `BridgeCore`; nothing tests the executable.

## The Extension's toolchain

esbuild, driven by `extension/build.mjs`: bundle the three entry points (background, popup, Relay page), copy the two HTML files, write both manifests, and zip. About forty lines and one dependency.

Vite was rejected because everything it is good at here is unusable. An extension has to be loaded from disk in a real browser, so there is no dev server or HMR to have, and MV3 background bundling means fighting the config to stop code splitting. Vitest stays regardless; it carries its own Vite internally, and that is not a reason to adopt Vite as the bundler.

Checks are `tsc --noEmit` and a Prettier format check. No ESLint or oxlint in v1, on a codebase of roughly four hundred lines that the type checker already covers.

pnpm with a committed lockfile, installed in CI from its public action, so nothing in the repo depends on a particular local toolchain manager being present.

## Generated constants

`tools/generate.mjs` reads `identity-providers/entra.json` and writes two files:

- `bridge/Sources/BridgeCore/Generated/EntryOrigins.swift`
- `extension/src/generated/entryOrigins.ts`

Both are committed with a do-not-edit header, and CI regenerates them and runs `git diff --exit-code`, so a hand-edit or a stale file fails on the commit that caused it. The generated manifests stay build artifacts in `dist/`, since nothing imports them.

Committing the outputs rather than gitignoring them keeps each toolchain independently usable: with the Swift constant generated by a Node script and never committed, `swift build` and `swift test` would not work from a clean clone until someone ran Node. The alternative that keeps nothing committed is a SwiftPM build-tool plugin, which costs a plugin target, a tool target, and the plugin sandbox's rules, all for one array of URLs. ADR 0003's actual concern, the origins differing between the two halves, is impossible either way because both outputs come from one file in one run.

## The two manifests

Two complete committed JSON files, `manifest.chromium.json` and `manifest.gecko.json`, each readable end to end and differing openly where the engines differ: `incognito: "split"` and the `key` field that pins the extension ID in Chromium; `browser_specific_settings` carrying the add-on ID and `strict_min_version` in Gecko; `background.service_worker` against `background.scripts`.

The build parses each, sets `version` and `host_permissions`, and writes the result to `dist/`. No placeholder strings and no base-plus-overlay merge: the differences are the interesting part of these files, and a merge algorithm would move the real manifest into the build script where nobody can diff it against the browser documentation.

## Version

The git tag is the only source. `build-app.sh` and `build.mjs` take a `--version` argument defaulting to `0.0.0`, and the release workflow passes the tag with its leading `v` stripped into `Info.plist`'s `CFBundleShortVersionString` and both manifests' `version`. Extension manifests accept only a dotted numeric version, which is why `git describe` output is not used directly.

No committed VERSION file, so there is no second place for the number to disagree with the tag and nothing to remember to bump before tagging. A locally built pair reads `0.0.0`, which is visibly not a release rather than impersonating one.

## Building the .app

`packaging/build-app.sh` runs `swift build -c release`, lays out `Contents/MacOS` and `Contents/Resources`, substitutes the version into `Info.plist`, copies `assets/EnterpriseSSOBridge.icns`, and runs `codesign --force --sign -` for the ad-hoc signature the caller-authentication story assumes on the other side.

No Xcode project. It would buy asset catalogs and UI testing for a target that has one icon and no UI tests, in exchange for a project file to maintain and merge, and CI would need more than the toolchain.

## Workflows

Both on `macos-26`, currently `macos-latest` and GA on arm64, which satisfies the macOS 26 floor. Every action pinned to a full commit SHA. The workflow verifies the runner's `swift --version` against what the package requires rather than trusting the image to carry the right toolchain.

`ci.yaml`, on push and pull request: regenerate and `git diff --exit-code`, `swift-format lint`, `swift build`, `swift test`, `pnpm install --frozen-lockfile`, `tsc --noEmit`, the Prettier check, Vitest, then build both extension bundles plus the `.app` and the `.pkg`. Packaging runs here on purpose, so a packaging break surfaces on the commit that causes it instead of when you are trying to cut a release.

`release.yaml`, on `v*` tags: the same build with the tag's version, producing the `.pkg`, the `.crx` packed with the private key from an Actions secret, the `.xpi`, and `install-chromium-extension.sh`, attached to a GitHub release. Tagging therefore exercises nothing CI has not already done except the signing key.

## Packing the .crx

`tools/pack-crx.mjs`, about sixty lines of `node:crypto` and hand-written protobuf, chosen over the runner's Chromium binary. It adds no dependency: CRX3's two messages use only length-delimited fields, and the signature is RSA PKCS#1 v1.5 over SHA-256, which `node:crypto` signs directly.

`--pack-extension` was a live option rather than a straw man. The `macos-26` image does ship Google Chrome, installed by `images/macos/scripts/build/install-chrome.sh` and listed in `macos-26-arm64-Readme.md` at 152.0.7977.83, and the same version on this Mac packed the built bundle successfully. What that costs is a full browser launch in CI with its own user-data directory, an output path fixed to the input directory's name, and an artifact whose format is whatever the image's Chrome happens to be that week. The packer is the same code locally and on the runner, and it fails loudly when the signing key does not derive the ID that `manifest.chromium.json` pins.

The format is Chromium's, read from `components/crx_file/crx3.proto` and `crx_verifier.cc` rather than from a description of it: `[Cr24][3][header length][CrxFileHeader][zip]`, with every signature covering `"CRX3 SignedData\0"` plus the little-endian length of `signed_header_data` plus `signed_header_data` plus the zip. Chrome's own output was decoded to confirm the field numbers, the PKCS#1 padding rather than the PSS the proto comment mentions, and the 16-byte `crx_id`. A package from `pack-crx.mjs` and one from Chrome for the same bundle and key produce the same header size and the same `crx_id`, and Helium installed the packed one from an external-preferences file into an isolated profile with `location=2` and `disable_reasons=[8192]`, the acknowledgement state `install.md` describes.

The private key lives outside the repository and reaches the release workflow as the `CHROMIUM_EXTENSION_KEY` Actions secret, written to a mode-0600 temporary file for the length of one step.
